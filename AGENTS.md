## Как работаем

- Это обучающий проект: объяснять подробно и давать писать код и выполнять настройки самому, если не просит сделать за него.
- Работаем по методике GitHub Flow.
- Пушить только когда об этом попросили.
- Общение и документация — на русском; код, имена и сообщения коммитов — на английском.
- Один шаг за раз: сначала объяснить, что и зачем делаем, затем дождаться подтверждения. Не создавать файлы и сервисы «на будущее».
- Проверять результат командой, а не на глаз: `docker compose config`, `ruff`, `pyright`, `pytest`.

## Проект

Учебный проект «Аналитика бронирований»: генератор → RabbitMQ → ClickHouse → Superset и Jupyter. Система поднимается через `docker compose`. Репозиторий и CI — GitLab (`.gitlab-ci.yml`).

Стек: Python 3.13, Docker Compose, ClickHouse, RabbitMQ, Superset, Postgres, Redis, Jupyter. Проверки: ruff (линтер и формат), pyright, pytest.

## Зоны ответственности

- Лев: `docker-compose.yml`, `clickhouse/init/`, `generator/`, `consumer/`, `tests/`, CI.
- Амир: `superset/`, `jupyter/`.
- Вместе: схема ClickHouse, аналитические вопросы, README.

Не менять файлы чужой зоны без просьбы. Изменение общего контракта — схемы таблиц, имён переменных окружения, `docker-compose.yml` — сначала обсудить: на него опираются обе зоны.

## Ветки и пуш

- `main` защищена: прямой push сервер отклоняет. Изменения — только через ветку и merge request.
- Ветка на задачу: `feature/<задача>` или `fix/<что>`, живёт 1–3 дня.
- Порядок: `git switch main && git pull`, затем `git switch -c feature/<задача>`.
- Пушить — только когда попросили: `git push -u origin feature/<задача>`.
- Если push в `main` отклонён — не обходить защиту (`--force`, смена настроек), а перенести коммиты в ветку: `git switch -c feature/<задача>` (коммиты останутся на месте) и запушить её.
- После merge: `git switch main && git pull && git branch -d feature/<задача>`.
- Squash не используем: в `main` попадает merge-коммит с историей ветки.

## Секреты и конфигурация

- Пароли и настройки — только в `.env` (он в `.gitignore`); в репозитории лежит `.env.example`.
- Новая переменная в коде или Compose — сразу строка в `.env.example`.
- Значения по умолчанию в коде не хардкодим: читаем из окружения.

## Зависимости

- Зависимости сервиса — в его `requirements.txt`, с ограничением версий (`>=x,<y`).
- Новую библиотеку добавляем только под конкретную задачу, а не «может пригодиться».


## Коммиты

Сообщения коммитов — по [Conventional Commits](https://www.conventionalcommits.org/):
`<тип>: <что сделано>` или `<тип>(<область>): <что сделано>`.

- На английском, в повелительном наклонении, с маленькой буквы, без точки в конце:
  `fix(search): escape like wildcards`
- Не подстраиваться под стиль последних коммитов в истории — часть из них написана без типа.

| Тип | Когда |
|---|---|
| `feat` | новая возможность для пользователя |
| `fix` | исправление бага, включая UI и безопасность |
| `refactor` | перестройка кода без изменения поведения |
| `perf` | ускорение |
| `test` | тесты |
| `ci` | GitLab CI, деплой |
| `build` | Dockerfile, зависимости |
| `chore` | всё остальное (`.gitignore`, конфиги) |
| `docs` | документация |

- `style` — только форматирование кода, не изменения внешнего вида (это `feat` / `fix`).
- `refactor` не меняет поведение; если поведение меняется — это `feat` или `fix`.
- Если коммиту подходят несколько типов — его стоит разбить.
- Область по желанию: `auth`, `search`, `profile`, `events`, `migrations` и т.п.
